# Saved reading visual replay

This implementation is prepared and verified locally with fake providers. Visual provider, migration and DO production gates remain closed.

An explicit POST is the only action that can start a saved-source visual replay. Cloud replay takes its exact raw Markdown, ordered cards/orientations, deck, question and every supplied reflection from the authenticated owned journal row. Local replay takes explicitly submitted prose/context and discards old result IDs, bindings, capabilities and cached sidecars as authority. It does not regenerate prose.

The endpoints are `POST /api/journal/:entryId/visual-retry`, `POST /api/tarot-reading/visual-retry`, and independently authorized `GET /api/tarot-reading/visual-replays/:visualJobId`, `GET .../stream`, `POST .../cancel`. Cloud requires the existing personal Plus/Pro journal entitlement. Free personal accounts use the local submission endpoint. Service accounts are refused.

The private response handle contains `readingResultId`, `visualJobId`, `attemptId`, `visualJobToken`, `visualBinding`, `expiresAt`. Narrative identity and an existing matching binding stay stable; the new server-issued transport ID addresses a fresh DO. Public journal GET/list responses never contain capabilities. Clients must keep handles in private account/principal storage and guard updates by source, entry, state version and active attempt.

Replay is unavailable without D1, the DO binding, valid visual provider/model configuration, and explicitly configured `VISUAL_REPLAY_LIMITS`. That setting is JSON with positive safe-integer `rateLimit`, `windowMs`, and `totalLimit`. It has no default, no unlimited sentinel, and no subscription quota inference. Rate and lifetime inference counts include uncertain, failed, cancelled and revoked reserved calls. Dedicated replay claims enforce the policy; the existing feature-usage CHECK and feature names remain unchanged.

Authenticated admission comes from server-authenticated request context. Guests get a random HttpOnly `visual_replay_principal` cookie; only its hash and principal/aggregate identity enter the guest table. Guest aggregate identity requires an actual Cloudflare edge request and `CF-Connecting-IP`, or an explicitly trusted local `VISUAL_REPLAY_TRUSTED_IDENTITY.resolve(request)` binding. Forwarded/client owner/namespace headers and anonymous fallback are refused. Rotating the guest cookie does not reset the aggregate rate/total budget or grant access to another principal's work.

A claim is unique on the full source fingerprint and admission scope, independently of local entry IDs or transport IDs. Claim and journal-state linkage are conditional D1 transactions. Claim version and journal version are independent. Every final result/state/link commit checks active attempt/version, owner, deletion tombstones and actual captured narrative/cards/question/reflections/deck fields. Original jobs and older attempts cannot overwrite a successor.

A durable dispatch reservation precedes provider invocation. Explicit retry may resume a prepared attempt after readiness/offline failure; restore, readiness, status, stream, reconnect and cold start never dispatch. A server-side configuration check that proves zero invocation may release its reservation. Provider error labels never release it. An uncertain reserved attempt becomes exhausted on cold recovery, even when no response exists. A D1 commit completed before DO storage failure is reconciled without another call. The existing timeout is 30000 ms by default, capped at 60000 ms, and cancellation aborts the active provider signal.

Validated cached cues remain readable through unavailable or failed successors. A same-owner current registration can repair attachment without inference. Only a validated conditional successor changes the saved snapshot. Expired/revoked original capabilities are never reopened by `/init`; fresh replay uses a separate DO mode with one full saved snapshot and no original prefix/coalescing loop.

Journal detail/list derive expiry for incomplete original transports from their persisted expiry time, including an owned unlinked registration, both before and after the original expiry service persists expired status. They expose `expired` attachment and `available` retry state before any transport is awakened, preserve accepted cues and exact saved prose, and leave complete cached repairs at zero calls. An original cold DO checks replay supersession, actual parent source, owner and deletion fences before adopting durable state, scheduling recovered work and dispatching after asynchronous preparation. Superseded private work is revoked; it cannot adopt a replay ledger as original work or reopen its old capability.

Schema additions are in local-only migration `0037_reading_visual_retry_state.sql`, including immutable claim source/context, separate aggregate accounting, captured journal version and guest principals. No migration has been applied remotely. Release checks, physical/real-account review, live-provider qualification and production rollout remain separate gates.

## Journal client

The journal entry shows plain status beside the readable prose: "Your reading is saved. Card connections are unavailable." with a **Retry card connections** button only for an eligible failed, expired or missing saved visual. Pending, exhausted, revoked and explicitly unavailable states show status without another action. `useJournal().retrySavedVisuals(entryId)` is the only caller of the retry routes; mount, polling, stream reconnect, reload and account changes never call them. A cloud retry names only the owned entry. A local or guest retry submits only the saved prose, cards, deck, question and reflections.

The private replay handle is stored per owner and entry under `tarot_visual_resume:<owner>:entry:<entryId>`, never in entries, exports, shares, DOM attributes or `reading-visual-snapshot` event details. Original result-keyed handles keep their format. Removing or replacing a replay handle must name its attempt. Entries keep only the public projection `{ attachmentStatus, retryStatus, sourceFingerprint, stateVersion, reason }`.

Every asynchronous completion rechecks the current owner, the existing entry, the exact saved source and the expected state version, and for replay results the active attempt. Late work patches only a matching existing entry; it never inserts or recreates one. Local replay results are adopted only when their binding hashes match the saved source and the ledger covers the exact saved prose. Cloud completion refreshes the owned journal entry instead. A failed or empty successor keeps the previously validated cached snapshot. An explicit retry that finds replay unavailable is recorded as status only for the same source and state version.

Restored and re-annotated entries render statically. Manual literal, pair and identity inspection still works. Browser coverage uses the real route handlers with in-process D1 and a fake provider; it is not real-account, device or live-provider evidence.

## Claim retention

Claims intentionally outlive entry deletion so that deleting and re-saving cannot reset an allowance. A claim keeps the captured saved source (prose, question, reflections, cards and deck), its binding and a visual token. Deleting an entry or an account only marks its claims revoked (account deletion also writes a revocation tombstone and removes journal visual state); no purge exists yet. Guest claims carry an aggregate scope derived from a hash of the client IP and a guest principal. Choosing a purge and retention policy, and updating the privacy policy, is a release blocker recorded in the [readiness record](superpowers/reviews/2026-10-10-reading-cue-readiness.md).
