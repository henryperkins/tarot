# Personalized Reading Gestures React Bridge Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a React bridge that can spotlight any of the deck's 78 cards, proving its streaming, imagery, emergence, hold, relationship, and revisit behavior with the three existing recorded studies before production rollout.

**Architecture:** Reconcile the existing `feat/reading-card-touch` foundation before extending its Markdown annotations, focus provider, and artwork component. Use canonical card identity plus spread occurrence for every card; one focus engine consumes validated passage targets and actual visible-source progress, while artwork detail/motion recipes belong to a particular edition. The initial opt-in bridge runs all three recorded studies through application components; ordinary production readings retain their current usable prose and inspection until a reliable passage-association contract and production assets are ready.

**Tech Stack:** React 19, existing React Markdown/remark pipeline, existing `motion` dependency and `src/lib/motionAdapter.js`, native Web Animations API where needed, Node's test runner, and Playwright with controlled SSE fixtures.

**Spec:** [Personalized reading imagery and motion proposal](../specs/2026-10-08-reading-imagery-motion.md), [playable study and provenance](../../../output/reading-motion/README.md), [product](../../../PRODUCT.md), [design](../../../DESIGN.md), and [design contract](../../design-contract.md).

**Scope and current evidence:** The standalone living Star, Hermit/Wands relationship, and [five-card dialogue](../../../output/reading-motion/five-card-dialogue.html) already exist. All three are inputs to Tasks 3–7, not future extraction work. Their study checks do not complete the React tasks. Implementation was subsequently approved. The execution record below distinguishes the completed opt-in bridge from full-deck and production rollout work.

**Full-deck destination:** Any major, numbered minor, or court card can become the subject, return later, or participate in a relationship. There is no Star-only renderer, five-card whitelist, or linear unlock sequence. Every card must support whole-card emergence, focus, settlement, orientation, hold, and revisit through the same engine. The finished experience also needs supported imagery and an intentional motion treatment for every card in the adopted edition; some imagery may call for still illumination rather than moving a figure or symbol. Unsupported detail fallback keeps a reading usable during development but does not count as finished deck coverage. Task 4 proves the common path across all 78 identities; Task 8 records the remaining per-card work and gates a claim of full-deck completion.

## Global Constraints

- “Preserve its current prose, headings, section structure, and interpretive depth.” Do not rewrite recorded or generated readings to fit animation.
- “Use hand-authored semantic cues tied to exact fixture passages for this prototype. An automated semantic-tagging system is not required.” This bridge has no new live generation, paid API calls, or generalized tagging service.
- “Streaming introduces associations.” Source delivery continues during held inspection; holding pauses the visual accompaniment, not the SSE connection or model job.
- “Explicit reader inspection takes priority and holds the association.” Completed and restored readings retain revisit access without replaying a cue backlog.
- “If text arrives quickly, coalesce cues rather than rapidly playing a backlog.” Retain at most one latest pending automatic association.
- “Do not force scrolling or assume text arrival proves gaze position.” Visibility gates motion; it is not an eye tracker.
- “Keep Tableu’s established Source Serif headings and Inter reading copy.” Preserve native paragraph/list semantics and existing heading/TTS/HTML policies.
- “Reflections are optional.” Production context consists of the actual question and optional `reflections[spreadIndex]`; do not manufacture a general reflection.
- “Respect reduced-motion preferences with static associations that preserve the same meaning.” Add no playback button, continuous pulse, diagnostic rings, or instructional engagement toolbar.
- This is an Operate + Read surface: motion connects passage meaning to actual artwork and preserves spread memory. Acknowledge activation immediately, with optional feedback lasting 100–150 ms; source delivery and inspection never wait for a transition to finish.
- Use the current study values initially: presence `0` and hidden before introduction; `0.035` at physical-description start; quadratic ease-in to `0.55` at its authored midpoint; ease-out to `1` at description end. The artwork's resting layer is opacity `0.74` with `brightness(0.88)`; hover, keyboard focus, and held inspection brighten to `1`, retaining detail illumination and approximately `3px` lift. These are study values, not validated production reading-speed tokens.
- Emergence remains tied to available description progress, not a fixed 500–700 ms full reveal. Initial crossfade candidates are 300 ms exit / 550 ms entrance, with ease-out on exit and `cubic-bezier(0.16, 1, 0.3, 1)` on entrance. These replace the standalone 600/700 ms handoff timings for bridge evaluation, not its source-progress curve.
- Use `pool-pour` and `land-pour` consistently from literal description through interpretation and balanced payoff. Unsupported details fall back to the whole card.
- The canonical deck has 78 cards; the downloaded set's card back is an asset, not a 79th reading subject. Keep identity/occurrence, supported detail, passage, optional personal context, and reader-held state separate. A known detail alone never activates a gesture.
- Previously introduced cards remain available in spread order during and after the reading. Introduction state in the companion is separate from the application's tarot reveal state; an automatic cue cannot reveal an undrawn/unrevealed card.
- Preserve the living Star's masked water, including immediate release into a 1.5-second slowdown/fade followed by paused loops. Source delivery continues during every held inspection. Other authored details use finite gestures; do not transplant the Star's water treatment to unrelated cards.
- Permit one active cinemagraph presentation normally, or two only for an explicit authored relationship. Both Star pours belong to one card presentation. Shelf, departing, and duplicate detail-view copies remain static; an outgoing card's water stops immediately when motion ownership transfers. Offscreen, settled, and reduced-motion states have zero running loops.
- Keep original SVGs as image resources. Do not inline executable originals, copy the entire approximately 276 MB deck into production assets, or silently change production deck lookup/vision assets.
- Work in an isolated execution worktree, stage only owned paths, and preserve earlier studies and unrelated changes. This document authorizes no implementation, merge, push, deployment, or release by itself.

## Motion architecture review

Use scoped WAAPI/CSS and the existing motion adapter as the recommended bridge baseline, with React-owned incoming/exiting artwork layers. Start with restrained focus-window crossfades. A shelf-to-focus FLIP is an optional spatial-continuity study, not a prerequisite: keep the shelf card in its original slot, use a separate React-owned presentation, batch geometry reads before transform writes, and cancel on replacement/resize. Large automatic flights must justify the additional distraction on this Read surface.

WAAPI does not guarantee compositor-only work. The study animates SVG dash offsets and uses masks/filters; those can require painting. Avoid per-frame React state updates, retain handles across unrelated source appends, and profile the actual painted area and dropped frames. Target smooth rendering on a mid-range handset; do not claim locked 60 fps, universal support, zero jank, or zero React renders while prose continues streaming. Feature-detect required controls and retain static fallback. [Rendering guidance](https://web.dev/articles/animations-guide)

View Transitions remain a possible later enhancement. Same-document `document.startViewTransition()` is Baseline 2025 across current major browsers, including Firefox; cross-document support is a separate question and irrelevant to an in-place companion handoff. Feature-detect it, preserve fallback, assign unique transition names to rendered elements, and avoid snapshotting the changing prose. Shelf and focus copies cannot simultaneously share one transition name. `@starting-style` can support CSS entries but does not provide semantic timing or reading association. [Same-document API](https://developer.mozilla.org/en-US/docs/Web/API/Document/startViewTransition), [transition names](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/view-transition-name), [starting styles](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@starting-style)

Canvas/OffscreenCanvas is a profiling-led alternative if bounded SVG overlays cannot meet the device budget. It need not replace the SVG base artwork: a transparent, correctly sized overlay can preserve crisp card imagery. Worker rendering is possible, not automatic; sizing, occlusion, visibility, accessible DOM controls, cleanup and context-loss fallback still need coordination. Account for device-pixel ratio and backing-store memory before claiming a performance advantage. No Canvas/Worker renderer is added by this plan. [OffscreenCanvas API](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas)

### Task 5: Extend the single focus engine with hold and coalesced accompaniment

**Files:** Create `src/components/reading/narrative/narrativeGestureState.js`; modify `NarrativeCardFocus.jsx`, `src/hooks/useNarrativeReadingLine.js`, `NarrativePanel.jsx`, `src/hooks/useReadingSelection.js`, `src/components/ReadingDisplay.jsx`, and the panel/controller callback plumbing. **Interfaces:** `createGestureFocusState({ runId, sourceRevision, associations = [], introductions = [], completed = false }) -> FocusState`; `reduceGestureFocus(state, event) -> FocusState`. Events are `{ type: 'PROGRESS', progress, eligibleAssociationIds, now }`, `{ type: 'VISIBLE', kind: 'passage' | 'artwork', id, visible }`, `{ type: 'HOLD', selection }`, `{ type: 'RELEASE' }`, `{ type: 'INSPECTION', kind, active, occurrenceId }`, `{ type: 'SOURCE', source, associations, introductions }`, `{ type: 'STATUS', status }`, `{ type: 'MOTION', reducedMotion }`, and `{ type: 'TICK', now }`.
